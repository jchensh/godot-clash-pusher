# 3D 战斗性能预算与近似测量（D8）

> 2026-10-25，PLAN_V5_3D D8。目标：**手机稳定 30 帧**（每帧 ≤ 33.3 毫秒）。
> 目前没有真机，本文是**电脑上的近似测量**。真机实测记为欠账（见文末）。
> 按用户决策，D8 测量后**没有做任何降配**。之后用户要求做画质三档（D8b），方案和实测见第 5 节。

## 1. 预算（D8 定稿，等真机复核）

| 项目 | 预算（每帧） | 30 单位实测（p95） | 结论 |
|---|---|---|---|
| 场上存活单位 | 设计上限 40，常态 ≤ 30 | 34 | ✅ |
| draw call（含描边、阴影） | ≤ 500（D8b 低档另设：3D 部分 ≤ 150） | D8 原状 **674**；D8b 高档 459 / 低档 216（仅 3D 131） | ✅ D8b 后达标，见 §5 |
| 三角面（含描边、阴影） | ≤ 55 万 | 41.9 万 | ✅ |
| 同屏骨架 / 骨骼 | ≤ 45 个 / ≤ 300 根 | 34 个 / 212 根 | ✅ |
| 同屏特效件 | ≤ 120 | 56（满场 60 单位时 83） | ✅ |
| 静态内存 | ≤ 150 MB | 61 MB | ✅ |
| 显存（1080 宽物理分辨率） | ≤ 200 MB | 96 MB | ✅ |
| 手机主线程 CPU（逻辑 + 表现 + 提交渲染） | ≤ 20 毫秒 | 推算 13~20 毫秒 | ⚠️ 贴近上限 |
| 手机 GPU | ≤ 25 毫秒 | 电脑推算不可靠，需真机 | ❓ |

## 2. 测量方法

- 工具：`tools/perf_battle_3d.gd`（可重跑）。打开真实的正式战斗页，双方持续补兵，把场上存活单位维持在指定数量。25 种正式模型轮换出场，都带骨骼动画。每秒交替放一张法术，10 种轮换。远程开火、受击、阵亡等特效自然产生。塔设为打不掉，保证测量窗口内一直是满场。
- 条件：
  - 窗口用手机竖屏逻辑分辨率 750×1334；
  - 3D 渲染倍率 1.44，相当于 1080 宽手机的物理像素。项目拉伸模式是 `canvas_items`，手机上 3D 按屏幕物理像素渲染；
  - 渲染器是 Compatibility（gl_compatibility），和手机包一致；
  - 热身 3 秒后，逐帧采样 15 秒。
- 电脑：RTX 4080 SUPER。显卡驱动强制垂直同步（144Hz），所以「帧间隔」不能当耗时看。耗时只看以下三项：
  - 页面处理（逻辑 tick + 3D 同步 + 特效 + HUD）的计时；
  - 渲染 CPU；
  - 渲染 GPU。
- 命令示例（D8b 起：`--quality` 选档，`--phys 1.44` 模拟 1080 宽物理分辨率，`--no2d` 只量 3D 部分，`--no-fx` 关特效对照）：

```bash
godot --path . --resolution 750x1334 --script res://tools/perf_battle_3d.gd -- --units 30 --seconds 15 --quality low --phys 1.44
```

## 4. 换算到手机（近似）

- **CPU**：中端手机单核性能约为这台电脑的 1/4~1/6。
  - 30 单位：主线程 p95 ≈ 1.94 + 1.36 = 3.3 毫秒，推算 **13~20 毫秒**，在 33 毫秒以内；
  - 40 单位：推算 18~27 毫秒；
  - 60 单位：推算 29~43 毫秒，**可能跌破 30 帧**。
  - 2D HUD 绘制和引擎固定开销没单独计入，实际会再高一些。
- **GPU**：电脑 GPU 耗时只有 1~2 毫秒，而且主要是固定开销。渲染倍率从 1.0 提到 2.0，耗时只从 0.75 涨到 1.19 毫秒，所以不能线性推算到手机，必须真机测。改用两个间接指标判断：
  - 三角面 41.9 万：中端机每秒能处理上亿三角面，30 帧下压力不大；
  - draw call 674：Compatibility 渲染器每个 draw call 的驱动开销在手机上明显更高，这是最大风险。
- **draw call 的来源**：
  - 空场就已经有 234 个。场边栅栏、树、草丛、石头各自是独立网格，每个还要加描边和阴影两遍；
  - 每个单位约 8 个：模型、描边、阴影、阵营环、血条；
  - 特效平均约 +100，峰值约 +150。
- **结论**：
  - 30 单位以内，CPU 推算够用，内存和三角面都有余量；
  - draw call 超出常用预算，手机上能否稳 30 帧要看真机；
  - 近似测量**没有证明会掉到 30 帧以下，但风险明确**。按决策只报告，不降配。

## 5. D8b 画质三档（2026-10-25 实施，取代上一版「可选降配方案」）

用户 2026-10-25 要求做画质高 / 中 / 低三档，方案由 agent 决定。目标平台是微信、抖音小游戏，所以**低档就是小游戏基线**。代码在 `view/three_d/quality.gd`。

**所有档位通用（画面不变，纯省开销）：**
- 战斗页方向光阴影改为单层（正交俯视镜头不需要 4 层）；王国、主菜单、模型展示保持默认分层阴影，免得阴影发糊。
- 单位阵营脚环、单位和塔的血条合批：MultiMesh 一共 3 个 draw call，原来每个单位 3 个。容量不够时自动翻倍，不丢实例。
- 受击闪白的叠加层只在闪白那 0.15 秒挂上（原来常挂，每个网格多一个 draw call）。
- 河岸和外沿石沿合成一个网格。

| 项目 | 高 | 中 | 低（小游戏） |
|---|---|---|---|
| 实时阴影 | 全部 | 只有单位和塔 | 关掉，换成贴地圆影（1 个 draw call） |
| 描边 | 全部 | 单位、塔、特效 | 只给画面主体（战斗单位、王国建筑） |
| 3D 渲染倍率 | 1.0 | 0.85 | 0.7 |
| 网格 LOD 阈值 | 1 像素 | 2 像素 | 4 像素（引擎导入时自动生成的低模更早顶上） |
| 粒子 | 全量 | 6 成 | 不放 |
| 同屏可选特效上限 | 不限 | 120 | 60（法术和投射物不受限） |
| 骨骼动画 | 每帧 | 每帧 | 30 次/秒 |

- **档位选择**：
  - 电脑默认高，手机原生默认中，网页和小游戏默认低。
  - 每次启动只在第一局自动调一次：第 2~10 秒统计帧耗时 p90（单帧超过 250 毫秒的算切后台或追帧，不计入；有效样本不足 30 个就留到下一局），低于 20 毫秒下次进战斗升一档，高于 40 毫秒下次降一档。
  - 调档结果只在下次进 3D 页时生效；断线重连回到同一局不换档。
  - 设置页可以手动选（竖屏、横屏都有），手动选过之后不再自动调；手选会作废还没生效的自动调档结果。
  - 档位存在 `user://settings.cfg` 的 `[graphics]` 段，只是本地显示偏好。
- **实测**（同第 2 节条件，3D 倍率 = 档位倍率 × 1.44，平均 / p95；「仅 3D」= 隐藏 2D HUD 和飘字后的数据）：

| 场景 | draw call（含 2D） | draw call（仅 3D） | 三角面 | 渲染 CPU ms | 渲染 GPU ms | 显存 MB |
|---|---|---|---|---|---|---|
| D8 原状，30 单位 | 596/674 | — | 39.3/41.9 万 | 1.21/1.36 | 1.16/1.61 | 95 |
| 高，30 单位 | 373/459 | 294/351 | 30.7/32.9 万 | 0.86/1.00 | 1.06/1.15 | 93 |
| 中，30 单位 | 308/375 | 264/309 | 24.1/25.5 万 | 0.81/0.95 | 1.00/1.08 | 88 |
| **低，30 单位** | 190/216 | **116/131** | 18.5/19.8 万 | 0.63/0.74 | 0.50/0.76 | 85 |
| 低，40 单位 | 215/249 | 154/180 | 23.8/25.0 万 | 0.67/0.80 | 0.54/0.99 | 85 |
| 低，空场 | 68/69 | 24/24 | 1.5 万 | 0.37/0.43 | 0.28/0.30 | 81 |

- **结论**：
  - 低档 30 单位时，3D 部分 draw call 的 p95 为 131，达到 ≤150 的小游戏目标；
  - 剩下的大头是 **2D HUD 和飘字**，约 45~85 个 draw call，属于 2D 界面优化，不在 D8b 范围内，记为下一个风险；
  - 页面处理（逻辑 + 3D 同步 + 特效）三档相同，p95 约 1.9 毫秒；画质档只影响渲染。
- **还没做的**：
  - 场上单位上限按 40 设计（玩法层约束）；
  - 场边点缀和栅栏进一步合批（低档已经去掉描边和投影，收益变小）。
